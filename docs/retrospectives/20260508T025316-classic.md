## Run Summary

**Run ID:** 20260508T025316-classic

**Date:** 2026-05-08  
**Tests completed:** 9/9  
**Cluster detail:** classic-bench · ROSA Classic · Multi-AZ · us-east-1 · m5.xlarge · autoscaling 3–9 nodes

### Headline Numbers
- Cluster install: **60m 49s** — at the upper end of the expected 45–65 min range
- CAS scale-up: **22m 41s** — dominated by EC2 boot; ScaledUpGroup event variant required script fallback
- HPA response (ample capacity): **~2s** metric breach → pods Running; ~5m 16s total test time including workload deploy
- CAS scale-down: **9m 59s** — almost entirely the 10-min cooldown
- Overprovisioning (Test 09): **2m 41s** HPA → pods Running via pause-pod preemption; ~4.1× speedup vs Test 08

### Top Issues
- **Test 03: CAS event name variant.** CAS emitted `ScaledUpGroup` rather than `TriggeredScaleUp`. Script timed out waiting for `TriggeredScaleUp` after 10 minutes, then correctly fell through to watch for new nodes directly. No impact on result validity. Follow-up: script updated to watch both event reason variants.
- **Test 06: Container image missing required tools.** `ubi-minimal` does not ship `stress-ng` or `pgrep`. Workload was adapted to use `yes > /dev/null` for CPU burn and a no-op readiness probe; CPU utilisation was sufficient to trigger HPA at the 50% threshold. Fix applied going forward.
- **Test 08: Cluster saturation pre-condition.** Extra machine pools from Test 02 provided excess capacity, which would have prevented CAS from triggering. A capacity-filler deployment (45 replicas of pause pods) was manually deployed to saturate the cluster before the HPA trigger, ensuring accurate CAS cascade measurement. Harness gap: the Test 08 script should detect and handle multi-pool clusters automatically.

### Top Insights
- **EC2 cold start (~10–15 min) is the dominant latency in CAS scale-up at 22m 41s.** CAS decision came within ~1 min of FailedScheduling. Tuning CAS config has limited impact; pre-warmed capacity via overprovisioning is the highest-ROI mitigation.
- **CAS scale-down is almost entirely the default 10-min cooldown.** Drain time was under 2 minutes; the remainder was the `scale-down-delay-after-add` cooldown. Reducing to 5 min would halve scale-down latency for predictable workloads.
- **Overprovisioning with pause pods eliminated EC2 provisioning from the HPA hot path.** 2m 41s in Test 09 vs 11m 3s in Test 08 — a 4.1× reduction. Headroom was restored in ~3s post-burst via CAS background scheduling.
- **VPA advise mode is safe alongside HPA and surfaced under-provisioning.** cpu-burner was running at underprovisioned CPU requests; VPA target recommendations would improve HPA trigger accuracy and bin-packing under CAS.

## Test 05 — Unschedulable (CAS NotTriggerScaleUp)

**Status:** completed  
**Time to NotTriggerScaleUp:** 43s after FailedScheduling (5s to FailedScheduling, 43s to NotTriggerScaleUp)

### Issues Encountered
- _None._

### Key Insights
- CAS correctly refused to scale for a workload requesting more CPU than any m5.xlarge node can provide.
- `NotTriggerScaleUp` appeared within ~43s of FailedScheduling. This is the slowest NotTriggerScaleUp across all classic runs; later runs saw this in 4–12s.
- This is a common production misconfiguration: teams assume CAS will scale to accommodate any request. It will not change instance types. Proper fix: add a larger instance-type machine pool or split the workload.

## Test 06 — HPA Response

**Status:** completed  
**Time (metric breach → pods Running):** ~2s

### Issues Encountered
- `ubi-minimal` container image does not include `stress-ng` or `pgrep`. Workload was adapted in-run to use `yes > /dev/null` for CPU burn and a no-op readiness probe. CPU utilisation was sufficient to trigger HPA at the 50% threshold. Total test elapsed time was ~5m 16s due to workload deploy and metric accumulation, not scheduling latency.

### Key Insights
- 2s from metric breach to pods Running is consistent with HPA scaling on pre-warmed nodes: HPA decision fires in under 1s once the metric breach is detected; `yes > /dev/null` CPU burn drives utilisation above threshold quickly.
- The ~1 min of CPU metric accumulation (15s HPA scrape × ~4 windows) is the dominant factor when cluster capacity is available.

## Test 08 — HPA Triggers CAS

**Status:** completed (cluster saturation manually applied)  
**Total cascade time (HPA trigger → pods Ready):** 11m 3s

### Issues Encountered
- Extra machine pools from Test 02 were present when Test 08 ran, providing spare capacity that would have prevented CAS from triggering. A capacity-filler deployment (45 replicas of pause pods) was manually applied to saturate the cluster before the HPA trigger. Harness gap: Test 08 script should detect multi-pool clusters and apply the capacity-filler automatically.

### Key Insights
- 11m 3s is a true cold-start HPA→CAS cascade: HPA fired, pods went Pending, CAS triggered, new EC2 node provisioned, pods scheduled.
- This established the cold-path baseline for Classic. Later runs (Test 08 in 20260511T041449-classic, 46s) benefited from a pre-warmed node; this 11m 3s result remains the authoritative cold-start reference.
- The manual saturation workaround confirmed that multi-pool cluster topology must be controlled for in Test 08; later runs added `nodeSelector: pool-type: standard` to both cpu-burner and capacity-filler manifests.

### Issues Encountered
- _None._
