## Run Summary

**Run ID:** 20260510T193023-classic  
**Cluster type:** classic  
**Date:** 2026-05-10  
**Tests completed:** 9/9 core + test 12 (sudden spike)  
**Cluster detail:** classic-bench · ROSA Classic · Multi-AZ · us-east-1 · m5.xlarge workers · 6–22 nodes

### Headline Numbers
- Cluster install: **47m 38s** — fastest classic install, 16 min faster than the prior run (63m 39s on 2026-05-08)
- CAS scale-up: **15m 28s** — significant improvement over the first run (22m 41s); EC2 provision 5m 21s; node scheduling overhead 8m 5s
- HPA response (ample capacity): **~3s** metric breach → pods Ready (1m 20s total test elapsed including metric accumulation)
- Test 12 Phase 1 (no headroom): **9m 23s** surge → all pods Ready; Phase 2 (balloon pods): **2m 30s** — 3.7× improvement
- CAS scale-down: **12m 4s** — 2 min longer than prior run due to heavier drain workload; cooldown still dominant

### Top Issues
- **Multiple script bugs fixed during this run.** Five distinct harness issues were discovered and patched in-run: (1) `oc login` `--insecure-skip-tls-verify` prompting interactively in automation; (2) `NoneType` crash in `run-test-06-hpa.py` when HPA `currentMetrics` was JSON `null` during warm-up; (3) `cas-trigger.yaml` replicas too high (100) — reduced to 20 with `nodeSelector: pool-type: standard`; (4) `capacity-filler.yaml` replica count designed for a 2-node cluster — too few to saturate the 21-node multi-pool cluster; (5) `cpu-burner.yaml` missing `nodeSelector` causing pods to spread across all 21+ nodes and bypass the filled standard pool in Test 08. All five were fixed during the run; later runs benefited from the corrections.
- **Test 03: ScaledUpGroup event variant again.** CAS emitted `ScaledUpGroup` again (as in the first classic run). Script now watches both variants; fallback fired without impacting result validity.
- **Node scheduling overhead in Test 03 was unexpectedly large (8m 5s).** `node_ready_to_pods_running` was 8m 5s — dominated by image pull from the remote registry on a freshly booted node. The EC2 provision itself was only 5m 21s.

### Top Insights
- **Script quality was the bottleneck in this run, not the cluster.** Five harness bugs were uncovered when running against a fresh larger multi-pool cluster. The fixes made are the most impactful engineering output of this run — they make all subsequent runs more reliable.
- **EC2 provision time stabilised at ~5–6 min** across both AZ-distributed standard pools (5m 21s here, down from ~10+ min in the first run). AMI cache warmth or lighter AZ load explains the improvement.
- **Bare-metal (c5.metal) takes ~20 min to provision.** 19m 41s in this run, consistent with the 19m 58s seen in the next classic run. Never rely on on-demand CAS scale-up for bare-metal workloads.
- **Test 12 (sudden spike) validated the balloon-pod pattern at the cross-phase level.** Phase 1 (no headroom): 9m 23s; Phase 2 (balloon pods pre-reserved): 2m 30s. The 3.7× speedup mirrors the Test 08 vs 09 result and confirms the pattern generalises to sudden traffic spikes, not just scheduled HPA events.
- **Overprovisioning delivered a 4.8× speedup (Test 08 → Test 09).** 9m 54s → 2m 3s. This run's clean Test 08 measurement (cold EC2 start, properly saturated standard pool) gave the most accurate baseline for overprovisioning ROI.

## Test 08 — HPA Triggers CAS

**Status:** completed  
**Total cascade time (HPA trigger → pods Ready):** 9m 54s

### Issues Encountered
- `cas-trigger.yaml` originally had 100 replicas — these spread across all pools and did not trigger FailedScheduling on the standard pool. Reduced to 20 with `nodeSelector: pool-type: standard`. Fix committed.
- `cpu-burner.yaml` was missing `nodeSelector: pool-type: standard`. Without it, pods spread across all 21+ nodes and bypassed the saturated standard pool. Fix committed.
- `capacity-filler.yaml` needed to be tuned for the larger multi-pool cluster — original 10 replicas could not saturate a 21-node cluster. Reduced replicas and added `nodeSelector` to fill exactly 1 m5.xlarge node. Fix committed.

### Key Insights
- 9m 54s is a clean cold-start HPA→CAS cascade: HPA fired → pods Pending (59s) → CAS triggered → new node Ready (7m 10s) → pods Ready (1m 36s + 7s).
- This is the most reliable Test 08 result across all classic runs — the standard-pool isolation ensured the measurement was accurate.
- EC2 provision (7m 10s from CAS trigger to node Ready) accounts for ~72% of the total cascade time — confirming pre-warmed capacity is the dominant lever.

## Test 12 — Sudden Spike (advanced autoscaling)

**Status:** completed  
**Phase 1 (no headroom): surge → all pods Ready:** 9m 23s  
**Phase 2 (balloon pods): surge → all pods Ready:** 2m 30s

### Issues Encountered
- _None._

### Key Insights
- Phase 1 measured the unprotected spike path: HPA decision at 1s; pods Pending at ~4s; CAS triggered at ~5s; first node Ready at 9m; all pods Ready at 9m 23s. Matches the Test 08 cold-path baseline.
- Phase 2 demonstrated the balloon-pod pattern at burst scale: HPA decision still at 18s (metric accumulation); first pod Ready at 2m 30s — the balloon pods absorbed the initial spike without waiting for EC2.
- 3.7× improvement from Phase 1 to Phase 2 confirms the balloon-pod pattern generalises beyond the isolated HPA+CAS scenario (Test 09) to realistic sudden-traffic events.
- This was test 12 run out-of-sequence (after tests 01–09) on the same cluster without the full advanced autoscaling harness; results are valid as a standalone comparison.
