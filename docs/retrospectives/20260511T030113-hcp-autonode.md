### Top Issues
- **OCM 403 errors during Terraform apply required 22m retry sleep.** The `create.sh` OCM 403 backoff handler fired and waited 22 minutes before re-attempting apply. Cluster was provisioned successfully after the retry; IDP and IAM trust policy recovery followed the documented fallback path in `clusters/hcp-autonode/create.sh`. Total install time of 57m 54s includes this delay; without it, Terraform apply would have been ~22m 17s.
- **Test 07 (VPA advise) failed — N/A for ROSA HCP.** The VPA OLM operator pod remained Pending due to a `node-role.kubernetes.io/master` node selector. Control-plane nodes are in the management cluster and not accessible from the data plane in ROSA HCP. Marked as failed/N/A; VPA recommendations were not collected for this run.
- **Karpenter NodePool pre-created before tests 06 and 08.** `cpu-burner-karpenter.yaml` includes a Karpenter `nodeAffinity` that requires the `autonode-bench` NodePool to exist. The NodePool is normally created in test 10, but tests 06 and 08 on AutoNode clusters need it earlier. Pre-creation was done manually; this ordering dependency should be documented and automated in the skill.
- **Tests 12–13 required cluster re-provisioning.** The original cluster was destroyed after test 11. Tests 12 and 13 were run on 2026-05-12 on a freshly re-provisioned `an-bench` cluster (same Terraform config). The re-provision encountered an OCM 403 failure mid-way, requiring manual Phase 2 AutoNode setup (IAM trust policy update with correct OIDC provider URL, subnet/SG tagging). The test results are valid — same cluster type and NodePool configuration.
- **OIDC trust policy required manual correction after re-provision.** The existing `autonode-autonode-operator-role` had a stale OIDC provider URL from the previous (destroyed) cluster. The trust policy was updated manually to the new cluster's OIDC endpoint before AutoNode could operate.
- **Overprovisioning manifests required patches for Karpenter nodes.** The original `capacity-filler.yaml` and `pause-deployment.yaml` used `nodeSelector: pool-type: standard` which does not exist on Karpenter-managed nodes. Scripts patched to use `capacity-filler-karpenter.yaml` and `pause-deployment-karpenter.yaml`.

### Top Insights
- **Karpenter's scheduling decision is 6–10× faster than CAS but EC2 boot time is identical.** NodeClaim created within 1–8s of pods Pending; the node itself took ~4–5 min (EC2 boot). This means Karpenter's advantage is in scheduling throughput and decision speed, not in physical provisioning — it processes large pod batches in a single decision cycle rather than waiting for the full CAS loop per scale event.
- **Balloon pods are essential even with Karpenter.** Test 12 showed a 6m 34s degradation window on a sudden spike without preparation; adding 5 balloon pods reduced that to 1m 3s (84% improvement). Karpenter's faster NodeClaim decisions do not eliminate EC2 boot time, which remains the dominant factor.
- **Balloon pods + Karpenter is the highest-ROI pattern in this benchmark.** 7m 46s (test 08, no headroom) → 16s (test 09, balloon pods) — a 29× speedup. At 10 HPA events per day, this saves ~75 minutes of degraded user experience daily. Memory cost: 4 pause pods (~1 CPU / 2 GiB each) plus 1 idle Karpenter node.
- **VPA via OLM is not deployable on ROSA HCP.** The OLM-delivered VPA operator requires master-node access that is unavailable in the HCP data plane. Right-sizing on ROSA HCP requires load testing and HPA metric analysis instead. This is a permanent constraint, not a configuration issue.
- **Karpenter consolidation is dramatically faster than CAS.** First NodeClaim removed in 34s (test 10) vs CAS's 10-minute minimum unneeded-time. This translates to faster cost recovery after traffic subsides, but the `consolidateAfter: 30s` default causes pod rescheduling churn — tuning to `2m` is recommended for stateful or latency-sensitive workloads.
- **Parallel provisioning is mixed-path.** Test 13 showed 2/3 NodeClaims fulfilled from warm EC2 capacity (5s) and 1/3 from cold boot (4m 26s), producing a 4m 20s stagger. Do not assume Karpenter provides fully parallel provisioning; worst-case is still constrained by cold EC2 boot time per node.

**Workload:** 20 pause pods × 500m CPU / 512Mi (equivalent to cas-trigger.yaml)

**NodeClaim → first node Ready:** 4m 17s  
**Total (workload applied → all 20 pods Ready):** 8m 50s

### Issues Encountered
- Prior run (earlier 2026-05-12) used `karpenter-trigger.yaml` when it still had 100 replicas, measuring a mass 17-node provisioning event rather than a single-node scale-up. `karpenter-trigger.yaml` corrected to 20 replicas; 100-replica variant moved to `karpenter-trigger-100.yaml` for tests 10, 11, 13.

### Key Insights
- Karpenter decision latency: **1s** from FailedScheduling to NodeClaim created (vs CAS 34s — 34× faster). This is the scheduler reacting directly to the pod queue rather than running a poll loop.
- Node provisioning: **4m 17s** NodeClaim → node Ready (vs CAS 6m 4s — ~30% faster). EC2 boot time is the shared bottleneck; Karpenter's faster EC2 Fleet API call reduces the gap slightly.
- **AutoNode total time (8m 50s) is longer than CAS Classic (7m 33s)** despite faster decision and provisioning. Root cause: ROSA HCP workers carry more system daemonset pods (konnectivity-agent, kube-apiserver-proxy, OVN-Kubernetes), leaving less allocatable CPU per node. The same 20 pause pods overflow onto **4 new nodes** on HCP vs **1 new node** on Classic. Each of those 4 nodes pulls the pause image cold, serialising pod-start work. This is a Classic vs HCP infrastructure difference, not a CAS vs Karpenter one.
- The most directly comparable metric is **FailedScheduling → scheduler decision**: 1s (Karpenter) vs 34s (CAS). Both then wait on identical EC2 boot time.
- EC2 launch requested 5s after workload applied; node boot userspace 17.3s.

- Script initially warned that "NodeClaim count changed" during the 5-minute wait window, treating a _decrease_ as suspicious. The decrease was Karpenter consolidating residual nodes from Test 04 — not provisioning for the oversize pod. Fixed in `run-test-05-unschedulable.py` to only warn on NodeClaim _increases_.

### Key Insights
- Karpenter correctly refused to provision for a pod requesting 200 CPU / 1 TiB memory. No AWS instance type satisfies both constraints; this is physical infeasibility, not pool rigidity.

- CAS comparison: CAS emits `NotTriggerScaleUp` in ~21s and the event text explicitly states the reason. Karpenter is silent — operators must monitor NodeClaim creation (or absence) to confirm the autoscaler decision.
- For workloads that CAS refuses due to _pool rigidity_ (not physical infeasibility), see Test 05b: Karpenter can schedule a 28 CPU / 200 GiB workload by dynamically selecting r5.16xlarge — something CAS with m5.xlarge machine pools cannot do.
