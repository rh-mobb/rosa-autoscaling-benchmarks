Key Findings

  • Karpenter NodeClaim latency is 5–8s, compared to ~30–60s for a CAS scale-decision loop. For large bursts, this translates to ~2× faster end-to-end pod readiness.
  • EC2 boot time (~4–5 min) is the dominant bottleneck. Neither Karpenter nor CAS can eliminate it. Warm pools or balloon pods are the highest-ROI mitigations.
  • HPA response without headroom is 5m 0s (correctly measured with Karpenter manifests). With pre-reserved balloon pods (pause-deployment-karpenter.yaml), it drops to 22s — a 13.6× improvement via Karpenter preemption of low-priority pause pods.
  • VPA is not deployable on ROSA HCP via OLM. The standard operator requires master-node access unavailable in the data plane.
  • Karpenter consolidation adds scheduling churn. Pod stability after scale-down takes ~12m due to rescheduling across fewer nodes. Tune consolidateAfter conservatively for stateful or latency-sensitive workloads.
  • Machine pool provisioning is consistent at ~4m 30s for standard instance types. Bare-metal (m5.metal) takes 17m due to firmware initialization.

Recommendations

  1. Use AutoNode (Karpenter) for latency-sensitive, bursty workloads. The 6–10× faster scheduling decision and ~2× faster e2e make it the clear choice when pod startup latency matters.
  2. Deploy balloon (pause) pods for predictable HPA bursts. Pre-reserve 1–2 nodes of capacity using low-priority pause pods. Karpenter restores headroom automatically after eviction. This single pattern reduces HPA response from minutes to seconds.
  3. Don't invest heavily in CAS tuning for fast responses. CAS's architecture requires waiting for the scale loop; even with AutoNode clusters the default pool still uses CAS. Keep the default pool minimal and push bursty workloads to the AutoNode NodePool.
  4. For right-sizing, use manual profiling instead of VPA OLM. Run load tests and read HPA metrics; OLM-based VPA is not compatible with ROSA HCP's data-plane topology.
  5. Set consolidateAfter: 2m or longer for production NodePools. The 30s default caused aggressive churn during the consolidation benchmark. A longer window reduces unnecessary node replacements for bursty-but-sustained workloads.
