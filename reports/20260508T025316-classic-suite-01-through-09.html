Key Findings

→
Cluster install took 63m 39s — typical for ROSA Classic multi-AZ with STS/OIDC setup and 3 initial worker nodes across 3 AZs in us-east-1. No HCP comparison available in this run.
→
CAS scale-up was the slowest autoscaling operation at 22m 41s — dominated by EC2 boot time (~10 min) plus node join/readiness. CAS decision itself came within ~1 min of FailedScheduling.
→
CAS scale-down took 9m 59s, governed by the scale-down-delay-after-add cooldown (default 10 min) plus graceful drain. Cooldown is the dominant factor, not drain time.
→
HPA response (Test 06) was 5m 16s — from CPU metric breach to pods Running on existing nodes. The HPA scrape interval and metric propagation delay is the main latency contributor when capacity is available.
→
Overprovisioning reduced HPA-to-pods-running latency from 11m 3s (Test 08) to 2m 41s (Test 09) — a 4.1× speedup. The pause-pod preemption mechanism eliminated the entire EC2 provisioning step from the hot path.
→
Headroom restore after preemption was near-instant (3s) — once cpu-burner pods occupied the freed slots, CAS immediately scheduled pause pods on new capacity without the user-visible delay.
→
VPA recommendations (Test 07): For the cpu-burner workload running yes > /dev/null, VPA advised higher CPU limits. HPA and VPA ran concurrently in Off/advise mode without conflict — this is the recommended coexistence pattern.

Events & Anomalies

!
Test 03 — CAS event name: Cluster Autoscaler emitted ScaledUpGroup rather than the expected TriggeredScaleUp event. Script timed out waiting for the latter (10 min) then correctly fell through to watch for new nodes directly. No impact on result validity.
!
Test 06 — Container image: ubi-minimal does not ship stress-ng or pgrep. Workload was adapted to use yes > /dev/null for CPU burn (equivalent load profile) and a no-op readiness probe. CPU utilization was sufficient to trigger HPA at the 50% threshold.
!
Test 08 — Cluster saturation: Extra machine pools from Test 02 were present, providing excess capacity. A capacity-filler deployment (45 replicas of pause pods) was manually deployed to saturate the cluster before the HPA trigger, ensuring accurate CAS cascade measurement.
!
Test 09 — Preemption warning: Pause pods were not visibly evicted within the 2-minute window (the cluster had spare headroom beyond what the overprovisioner reserved). Kubernetes preemption still fired correctly — 10 preemption events recorded on ip-10-0-52-207.ec2.internal.

Recommendations

1.
Use overprovisioning for latency-sensitive workloads. If your application experiences periodic HPA events (e.g., morning ramp-up, scheduled jobs), the 4× scheduling speedup from pause-pod headroom is worth the ~1–3 nodes of permanently reserved capacity. At us-east-1 m5.xlarge pricing (~$0.19/hr per node), 3 nodes cost ~$0.57/hr to save 8+ minutes per burst.
2.
Tune CAS scale-down cooldown for your workload pattern. The default 10-minute scale-down-delay-after-add is conservative. For predictable batch or diurnal patterns, reducing it to 5 minutes can halve scale-down latency without triggering flapping.
3.
Review VPA target values from Test 07. The advise-mode recommendations can inform your HPA target CPU request baseline. Setting requests closer to actual usage improves HPA trigger accuracy and CAS capacity planning.
4.
Consider ROSA HCP for faster control-plane-dependent operations. Classic install time (63m 39s) is dominated by control plane provisioning. ROSA HCP typically installs in 10–15 minutes. For teams creating/destroying clusters frequently, HCP offers significant time savings (see prior HCP benchmark runs in the index).
