Key Findings

→
Cluster install took 47m 38s — 16 minutes faster than the previous run (63m39s on 2026-05-08). Difference is within expected variance for ROSA Classic multi-AZ STS provisioning. OCM ready at 45m42s; oc login succeeded at 47m16s; all ClusterOperators Available at 47m38s.
→
Machine pool provisioning ranged from 5m49s (compute, c5.4xlarge) to 19m41s (bare-metal, c5.metal). Standard m5.xlarge (9m51s) and memory-optimized m5.4xlarge (6m35s) show shorter warm-up. Bare-metal boot time is dominated by firmware/BIOS initialization (~5m44s for EC2 status checks alone).
→
CAS scale-up was 15m 28s from workload apply to pods Running. CAS decision itself came within 1m55s of FailedScheduling; EC2 node provision took 5m21s; node-level scheduling added 8m05s (image pull + kubelet init). FailedScheduling fired just 3s after workload apply.
→
HPA response (Test 06) was 1m 20s from manifests applied to pods Ready. The HPA scale decision fires in under 1s once the metric breach is detected; the 1m3s of CPU metric accumulation (15s scrape × ~4 windows) is the dominant factor when cluster capacity is available.
→
Overprovisioning reduced total HPA-to-pods-ready latency from 9m 54s (Test 08) to 2m 3s (Test 09) — a 4.8× speedup. The ~7m10s EC2 provisioning step was moved off the critical path. Headroom was restored in 4s after pods ran, showing CAS works asynchronously in the background.
→
VPA recommendations (Test 07): cpu-burner (yes > /dev/null) hit 199% CPU utilization. VPA advised raising the CPU request from 500m to 1168m (target) with a lower bound of 712m — the workload was under-provisioned. Memory recommendation was 256 MiB (vs 128 MiB requested). VPA and HPA coexisted safely in Off/advise mode.

Script & Skill Improvements Made During This Run

Fix: oc login TLS prompt (clusters/common.sh)
--insecure-skip-tls-verify=false prompted interactively in automation. Changed to =true so wait_oc_login_success runs non-interactively.
Fix: NoneType crash in run-test-06-hpa.py
HPA currentMetrics is JSON null (not absent) during warm-up. .get("currentMetrics", []) returned None → TypeError. Fixed with or [] fallback. Same fix applied to VPA containerRecommendations.
Fix: cas-trigger.yaml replica count & nodeSelector
Original 100 replicas scheduled easily across all pools. Reduced to 20 replicas; added nodeSelector: pool-type: standard to force pods onto the standard pool and trigger FailedScheduling predictably.
Fix: capacity-filler.yaml for multi-pool clusters
Original 10 replicas (designed for 2-node cluster) could not saturate a 21-node cluster from tests 01–07. Added nodeSelector: pool-type: standard and reduced to 5 replicas (fills 1 m5.xlarge standard node, leaving room for 1 cpu-burner but not 3).
Fix: cpu-burner.yaml missing nodeSelector
Without nodeSelector: pool-type: standard, cpu-burner pods distributed across all 21+ nodes, bypassing the filled standard pool in Test 08. Added nodeSelector so the HPA→CAS cascade is reliably demonstrated on the standard pool.
Process: cordon 2 of 3 standard nodes for Test 08
With 3 standard nodes and only 1 needing to be saturated, 2 nodes were temporarily cordoned with oc adm cordon before Test 08 and uncordoned after. This ensured deterministic FailedScheduling on the single schedulable standard node.

Recommendations

1.
Use overprovisioning for latency-sensitive workloads. The 4.8× scheduling speedup (9m54s → 2m3s) from pause-pod headroom is significant for services with burst patterns. At us-east-1 m5.xlarge pricing (~$0.19/hr), 2 headroom nodes cost ~$0.38/hr to save 7+ minutes per HPA event.
2.
Target machine pool nodeSelectors explicitly in benchmark manifests. All benchmark workload manifests (cas-trigger, cpu-burner, capacity-filler) should declare nodeSelector: pool-type: standard to avoid distributing across heterogeneous pools, which makes CAS cascade tests non-deterministic.
3.
Apply VPA recommendations to right-size the cpu-burner workload. VPA advised 1168m CPU (vs 500m requested). Acting on this would reduce the number of HPA replicas needed for the same load and improve CAS capacity planning accuracy.
4.
Clean up non-standard machine pools before autoscaling tests. The memory, compute, and bare-metal pools added in Test 02 persist through Tests 03–09, providing excess cluster capacity that interferes with tests designed for minimal cluster configurations. Consider deleting or scaling to 0 between test stages.
